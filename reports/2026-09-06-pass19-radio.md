Radio is built and both of the owner's stations play on the Apple TV. The two things nobody in
either project had ever observed are settled with measurements taken from AVPlayer on the device:
**AVPlayer follows the StreamTheWorld 302**, and **tvOS plays the `.aac` mount**.

Committed locally, **not pushed** — the push gate stands until the owner has tested it on Home
Theater.

Nothing on the do-not-touch list was approached. No station was added, edited, reordered or
deleted; the app is read-only against `/api/radio`. `Info.plist` was not changed and neither was
`project.pbxproj` (the target uses a filesystem-synchronized group, so a new `.swift` file in
`Marlin DVR TV/` joins it without a project edit). Nothing under `design/` was written. The only
requests this pass made to `192.168.1.250` were `GET /api/radio` and the two cached icon URLs it
returns.

### 1.1 The screen

Built to the app's look, not to frame 5g (owner, 2026-09-06) — the route the radar, Manage DVR and
Favorites took. Frame 5g draws eleven distinct values per station and `/api/radio` supplies three
(Pass 18 §3.6), so:

* **Dropped**, because the server has no data and no route that could have any: the frequency
  string in the 76 px square, the genre line, the now-playing programme, the track/artist line, the
  favourite star, the bitrate, and the volume slider.
* **Kept and filled**: the station name, and the count in the header.
* **Added**, and it is the reverse of a gap: the **icon the DVR has already fetched and cached**
  takes the square the design gave to a frequency string. It is the one field the server is
  generous with and the design had nowhere to put.

A tile is therefore the icon and the name, in a two-column grid, in the server's order. The
now-playing bar is the icon, the name and a Stop. The header keeps the design's own line
"Streams come straight from the station, not the DVR", which is literally true of what was built.

`format` is **ignored entirely** (owner decision). It is not drawn — and, far more important, it is
never handed to AVFoundation. See §2.

### 1.2 What the screen does when there is nothing to show

`handleRadio` has no failure path and always answers 200 (Pass 18 §1.6), so the two states that
matter are the server not answering and the list being empty. Both are said out loud, and both were
photographed on the Apple TV (§3.4):

* **Unreachable** — "The station list could not be read from the DVR." over the transport error
  itself: `transport error on /api/radio: Could not connect to the server.`
* **Empty** — "No radio stations yet." over "Stations are added on the DVR's own Radio page; this
  Apple TV only plays the list the server holds."

## 2. The player, and the three things it deliberately does not do

`RadioPlayer` is 243 lines and the whole of the playback is one of them:

```swift
let item = AVPlayerItem(url: url)          // RadioPlayer.swift:113
let player = AVPlayer(playerItem: item)
```

Grepped by hand after the diagnostics were removed, the three prohibitions hold with **zero code
matches** — every hit is in a comment saying why:

* **No play session.** No `POST /api/play/sessions`, no returned playlist URL, no first-playlist
  probe, no 10-second keep-alive. `PlaybackSession` is not imported or referenced. The contract is
  blunt: that route "is for TV/cameras and does not know about radio" (`HLS-CLIENT-API.md:307-309`).
* **No `AVPlayerViewController`.** The transport is the Radio screen's own SwiftUI bar.
* **No MIME option of any kind.** `AVPlayerItem(url:)` builds its `AVURLAsset` with **no options
  dictionary**, so AVFoundation reads the type off the wire. `AVURLAssetOverrideMIMETypeKey` is the
  trap the task named and it is not used: its header states that when a value is supplied "**only
  the specified MIME type is considered** … Any other information that may be available, such as
  the URL path extension or a server-provided MIME type, **is ignored**" (`AVAsset.h:550-552`).
  Passing the owner's `format` into it would make a label that is **empty on both live stations**
  authoritative over the truth from the CDN.
* **No `AVAudioSession` category and no `UIBackgroundModes`.** A grep for `AVAudioSession` across
  every Swift file in `Marlin DVR TV/` returns one hit, and it is the comment saying there is none.
  `Info.plist` is 13 lines and unchanged: one location string and `NSAllowsLocalNetworking`.

### 2.1 Never silence presented as playing

The bar only says NOW PLAYING when AVPlayer's own `timeControlStatus` reports `.playing`, which it
does not report until it is rendering. Three things can take it off that claim, each naming what
happened: the item's `status` going `.failed`,
`AVPlayerItemFailedToPlayToEndTime`, and a 20-second watchdog for a station that connects and then
produces nothing. `AVPlayerItemDidPlayToEndTime` is treated as a failure too — a continuous stream
has no end, so one arriving means the station went away. An error is reported in full: message,
failure reason, domain, code, and the underlying error.

There is no fallback anywhere. A station that will not play stays named on the bar with its own
failure text; nothing else is started in its place.

### 2.2 The lifetime

Owner decision: radio has the same lifetime as every other player in the app. `stop()` pauses,
calls `replaceCurrentItem(with: nil)`, invalidates every observation and removes every notification
token. It is called from `RadioScreen.onDisappear`, from the screen's Menu handler, and from
`UIApplication.didEnterBackgroundNotification`. A generation counter means a callback from a
torn-down item cannot repaint a bar it no longer owns.

This **overrides the design**, deliberately and on the owner's instruction: frame 5g's footer says
"Playback continues with the screen dimmed · Menu returns to the rail without stopping the stream"
(`dc:844`) and its caption says "playing while the screen stays up" (`dc:767`). Neither is built.

## 3. Step 6 — the two findings, station by station

Measured on **Home Theater**, Apple TV 4K (3rd generation), tvOS 26.6 build 23L773, driven by
`XCUIRemote` (the real remote's press pipeline), 2026-09-06.

Both readings came from a **disclosed temporary diagnostic** that is not in the committed build: a
line in the now-playing bar printing the codec AVFoundation decoded, the item's clock, its loaded
range and its access log, and a counter in the header of how many AVPlayers the app had attached
and not torn down. Both were removed before the commit and the acceptance run was repeated against
the stripped build (§4.3).

### 3.1 WBAL NewsRadio 1090 — the `.aac` mount — **plays**

`…/api/livestream-redirect/….aac`, the first station in the owner's order, and the one the server
project never reached even with curl ("the specific `.aac` call-signs I tried returned 404 … only
the MP3 path was verified end to end", marlin-dvr `…pass32…:110-119`).

On screen while playing (`reports/assets/pass19/atv-08-wbal-aac-codec-diagnostic.png`):

```
codec 'aac ' 22050Hz 1ch
clock 16.4s · loaded to 28.6s · likelyToKeepUp yes
attached AVPlayers: 1 [NOW PLAYING]
```

Ten seconds earlier the same line read `clock 6.0s · loaded to 18.0s`. The clock advanced 10.4 s in
ten seconds of wall time and the loaded range advanced with it: this is continuous audio being
decoded in real time, not a still frame of a hopeful UI.

**`'aac '` is `kAudioFormatMPEG4AAC`.** It is AVFoundation's own report of the track it decoded,
read off `AVPlayerItem.tracks.first?.assetTrack?.formatDescriptions`. That settles step 6b: **tvOS
plays the AAC mount.**

### 3.2 WCBM Talk Radio 680 — the `.mp3` mount — **plays**

`…/api/livestream-redirect/….mp3`. On screen
(`reports/assets/pass19/atv-09-wcbm-mp3-codec-diagnostic.png`):

```
codec '.mp3' 22050Hz 1ch
clock 16.2s · loaded to 26.3s · likelyToKeepUp yes
attached AVPlayers: 1 [NOW PLAYING]
```

Ten seconds earlier: `clock 5.9s · loaded to 16.3s`. Same shape, same conclusion.

### 3.3 The redirect — **AVPlayer follows it**

The premise, measured with curl this pass:

```
GET https://playerservices.streamtheworld.com/api/livestream-redirect/….aac
HTTP/1.1 302 Found
location: https://…….live.streamtheworld.com:443/….aac
connection: close
```

and, asked for the body size without following:

```
status=302 bytes=0
```

**Zero bytes, and no `Content-Type` header of any kind** on the 302 — the header list is date, the
three `access-control-*`, `cache-control`, `pragma`, `expires`, `location`, `x-stw-site`,
`connection`, and nothing else. Following it reaches a different host (a numbered
`*.live.streamtheworld.com` edge, and the number differs run to run) which answers
`HTTP/1.0 200 OK` with `content-type: audio/aacp` for the AAC mount and `content-type: audio/mpeg`
for the MP3 one.

So: AVPlayer, given only the redirector's URL, decoded AAC and buffered 28.6 seconds of it. There
are zero bytes of audio at that URL. **The only way it got audio is by following the 302 to the
CDN.** That settles step 6a.

**Said plainly, this is the one finding that is inference rather than direct observation.**
`AVPlayerItem.accessLog()` would have been AVFoundation's own record of the URI and server address
it ended at, and this pass looked: for both stations, on every sample over sixteen seconds, the log
existed and was **empty** — `access log: no events (log is empty)`. AVFoundation appears not to
write access-log events for a continuous progressive stream (they are an HLS-shaped facility). So
there is no line inside AVFoundation naming the CDN. The inference that replaces it is a tight one
— audio cannot come from a zero-byte response — but it is an inference, and it is Open Question 1.

## Open Questions

1. **The redirect finding is an inference, not a direct reading.** (§3.3) `AVPlayerItem.accessLog()`
   is empty for these streams on tvOS 26.6, so AVFoundation never names the CDN it reached. The
   argument — zero-byte 302, twenty-eight seconds of decoded AAC — is tight, but if the owner wants
   it observed rather than deduced, the way to do it is a packet capture on the network, which was
   outside this pass.
2. **The icon placeholder has never been seen with real data.** Both of the owner's stations have
   cached icons, so the empty-`iconUrl` path and the `/api/art/feed` 404 path were only exercised
   with staged data. A station whose icon the server cannot fetch will show the glyph; that is
   built and photographed, but never against the live server.
3. **Neither station has been heard.** Everything above is AVPlayer's report of itself. The one
   thing only the owner can confirm is that sound comes out of the television.
4. **The design's "playback continues with the screen dimmed" is now formally dropped** (`dc:844`).
   The owner's decision is explicit and this pass built to it. Worth naming because it is the one
   place the built app contradicts an approved design frame rather than merely omitting from it.
5. **What is the rule for a plain-`http://` station?** Still open, unchanged from Pass 18 Open
   Question 3. `NSAllowsLocalNetworking` does not cover a public host; today's two stations are
   `https://` so nothing is blocked, but the server accepts any URL the owner types on its Radio
   page, and such a station would appear in the list, look identical, and simply fail to play —
   with the app saying so, which is at least honest. Requiring `https://` or adding an
   `NSExceptionDomains` entry is the owner's call.
6. **The Home tile still reads "Stations", not a count.** Home reads five endpoints and
   `/api/radio` is not one of them; adding a sixth was not in this pass's steps. Every other built
   tile shows a number.
7. **The 20-second start watchdog is a number I chose.** It is generous enough for a cold CDN
   connection over the house wireless and finite so the bar cannot say "Connecting" for ever.
   Nothing measured it; if a station on a slow night gets cut off at twenty seconds, that is the
   place to look.
8. **`RadioUITests` is an evidence harness, not a standing test.** It needs the physical Apple TV
   and the owner's two stations, and it plays about a minute of live audio each run.
